# Introduction

The Identity Engine exposes its capabilities through secure, versioned, and well-defined APIs.

Every application within the AsBeez ecosystem—including web applications, mobile applications, AI Agents, partner integrations, and internal services—communicates with the Identity Engine exclusively through these APIs.

The APIs represent the public contract of the Identity Engine.

Their purpose is to expose business capabilities rather than database structures.

---

# Purpose

The Identity APIs exist to:

- Authenticate participants
- Manage identities
- Manage sessions
- Manage credentials
- Verify identities
- Manage trusted devices
- Support authorization
- Publish business events

Every API should remain consistent, secure, and backward compatible whenever practical.

---

# API Design Principles

Identity APIs follow the platform principles.

- API-First
- RESTful
- Stateless
- Versioned
- Secure by Default
- Resource-Oriented
- Idempotent where applicable
- Backward Compatible
- Event-Driven

APIs expose business capabilities.

They never expose internal implementation details.

# Authentication

Identity APIs support:

- Bearer Tokens
- OAuth 2.0
- OpenID Connect
- Service Accounts
- API Keys (Internal Services)

Every protected endpoint requires authentication unless explicitly designated as public.

---

# Authorization

Authentication identifies the participant.

Authorization determines whether access is permitted.

Every protected endpoint evaluates:

- Roles
- Permissions
- Policies
- Ownership
- Country Restrictions
- Authentication Assurance Level

# Standard Request Format

Requests should use JSON.

Example:

```json
{
  "email": "member@example.com",
  "password": "********"
}
```

---

# Standard Response Format

Successful responses should follow a consistent structure.

```json
{
  "success": true,
  "data": { },
  "meta": { },
  "links": { }
}
```

---

# Error Responses

Errors should follow a consistent format.

```json
{
  "success": false,
  "error": {
    "code": "AUTHENTICATION_FAILED",
    "message": "Authentication failed."
  }
}
```

Internal implementation details should never be exposed.

# Pagination

Collection endpoints should support pagination.

Example:

```text
?page=1
&page_size=25
```

Responses should include pagination metadata.

---

# Filtering

Collection endpoints should support filtering.

Examples:

```text
?status=active

?role=member

?verified=true
```

---

# Sorting

Standard sorting syntax:

```text
?sort=name

?sort=-created_at
```

A leading "-" indicates descending order.

---

# Searching

Search should support:

```text
?q=joey
```

Full-text search behavior should remain consistent across all platform engines.

---

# Idempotency

Operations that create or modify critical resources should support idempotency.

Examples include:

- Registration
- Password Reset
- Identity Verification
- MFA Enrollment

Clients should provide an `Idempotency-Key` header where appropriate.

---

# Rate Limiting

Endpoints should enforce configurable rate limits.

Examples:

Login

```text
5 requests / minute
```

Password Reset

```text
3 requests / hour
```

Public APIs

```text
100 requests / minute
```

Limits should be configurable.

---

# Versioning

Breaking changes require new API versions.

Minor enhancements should remain backward compatible.

Deprecated endpoints should remain available during the published deprecation period.

---

# Business Events

Successful API operations publish business events.

Example:

```text
POST /login

↓

UserAuthenticated

↓

SessionStarted
```

The API performs work.

Events notify the ecosystem.
