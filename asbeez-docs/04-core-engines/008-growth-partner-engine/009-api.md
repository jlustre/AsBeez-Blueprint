# Introduction

The Growth Partner Engine API exposes the business capabilities required to manage Growth Partners, Growth Partner Types, Growth Programs, relationships, Contributions, verification, performance, recognition eligibility, and Growth Partner lifecycle operations.

The API is designed around governed business actions rather than direct database access.

It supports:

- Growth Partner onboarding
- Growth Partner Type assignments
- Growth Program management
- Program enrollment
- Growth Relationships
- Contribution submission
- Evidence management
- Attribution
- Contribution verification
- Performance reporting
- Recognition eligibility
- Administrative review
- Appeals and corrections
- Internal platform integration

The Growth Partner Engine API does not issue Reward Points, create AsBeez Business Cells, distribute AsBeez Hive Credits, allocate Platform Revenue, or process Financial Settlements.

Those responsibilities belong to their respective engines.

---

# Purpose

The Growth Partner Engine API exists to:

- Register and manage Growth Partners.
- Assign and manage Growth Partner Types.
- Create and govern Growth Programs.
- Enroll Growth Partners in approved Programs.
- Record Growth Relationships.
- Submit and verify Growth Contributions.
- Manage Contribution evidence.
- Resolve attribution and duplicate claims.
- Retrieve Growth Partner Performance.
- Manage reviews, disputes, and appeals.
- Confirm recognition and incentive eligibility.
- Support administrative governance.
- Publish Growth Partner domain events.
- Integrate with other AsBeez engines and approved external systems.

---

# Guiding Principle

> **The Growth Partner API exposes governed growth capabilities while preserving strict separation between growth contribution, reward issuance, revenue allocation, ABC structure, AHC distribution, and financial settlement.**

---

# API Philosophy

The API should expose business capabilities rather than persistence operations.

Preferred actions include:

```text
Submit Growth Partner Application

Assign Growth Partner Type

Enroll in Growth Program

Record Member Introduction

Submit Growth Contribution

Verify Contribution

Resolve Attribution Dispute

Publish Performance Scorecard
```

Avoid implementation-oriented operations such as:

```text

Update Partner Status Column

Delete Relationship Record

Set Reward Amount
```

All public and internal endpoints should use terminology defined in the AsBeez Platform Glossary.

# API Surfaces

The Growth Partner API should be divided into distinct logical surfaces.

## Public Discovery API

Provides approved public information about active Growth Programs or public recognition.

Possible examples include:

- Public Growth Programs
- Public Growth Partner recognitions
- Public Ambassador profiles
- Public campaign information

Public endpoints must never expose private Contribution, attribution, dispute, or performance information.

---

## Growth Partner API

Used by authenticated Growth Partners.

Typical capabilities include:

- Manage Growth Partner profile
- View active Type assignments
- Browse eligible Growth Programs
- Enroll in Programs
- Submit Contributions
- Upload evidence
- View Contribution status
- View Performance
- Submit disputes or appeals
- View recognition

---

## Program Administration API

Used by authorized Program owners and administrators.

Typical capabilities include:

- Create Growth Programs
- Publish Program Versions
- Manage eligibility
- Manage Program limits
- Review enrollments
- View Program performance
- Pause or retire Programs

---

## Review and Verification API

Used by authorized reviewers.

Typical capabilities include:

- Review Contribution evidence
- Verify outcomes
- Resolve duplicates
- Assign attribution
- Request additional evidence
- Approve or reject Contributions
- Resolve appeals

---

## Internal Integration API

Used by other AsBeez engines and trusted services.

Typical capabilities include:

- Validate Growth Partner status

- Resolve Contribution eligibility

# Command and Query Separation

The API should logically separate state-changing commands from read-only queries.

## Commands

Commands request business actions.

Examples:

- Submit Contribution
- Approve Enrollment
- Verify Relationship
- Resolve Duplicate Claim
- Activate Growth Partner
- Publish Program Version

Commands may fail because of business rules.

---

## Queries

Queries retrieve business information.

Examples:

- Get Growth Partner Profile
- List Eligible Programs
- Retrieve Contribution Status
- View Performance History
- Retrieve Attribution Result
- List Recognition

Queries must not change business state.

---

# Business Actions

High-impact lifecycle changes should use explicit action endpoints.

Preferred:

```text
POST /growth-contributions/{id}/approve
POST /growth-programs/{id}/activate
POST /growth-partners/{id}/suspend
```

Avoid unrestricted status updates such as:

```text
PATCH /growth-contributions/{id}
{
  "status": "approved"
}
```

Explicit actions allow each transition to enforce authorization, validation, audit, and event publishing.

Completed and immutable records should reject modification entirely.

Successful business actions should publish domain events.

```text
Growth.GrowthPartnerActivated.v1

Growth.GrowthProgramActivated.v1

Growth.GrowthRelationshipVerified.v1

Growth.GrowthContributionApproved.v1

Growth.GrowthContributionIncentiveEligible.v1

Growth.GrowthPartnerPerformanceSnapshotCreated.v1
```

The API should not directly invoke downstream engine internals.

Other engines react through events or governed internal interfaces.

---

# Transactional Outbox

State changes and event records should be committed atomically through a Transactional Outbox or equivalent reliability pattern.

```text
Business State Change

+

Outbox Event Record

↓

Single Transaction

↓

Outbox Publisher

↓

Event Bus
```

This prevents a completed business action from becoming disconnected from its corresponding event.

# Business Rules

## GPE-API-001

Every state-changing request must be authenticated and authorized.

---

## GPE-API-002

Lifecycle transitions must use explicit business actions rather than unrestricted status changes.

---

## GPE-API-003

Completed Contributions, Relationship verification decisions, Performance Snapshots, and historical Program Versions must be immutable.

---

## GPE-API-004

Every Contribution submission must reference one Growth Partner, one Growth Program, one Program Version, and one approved Contribution Type.

---

## GPE-API-005

Only eligible and actively enrolled Growth Partners may submit Program Contributions unless retrospective submission is explicitly allowed.

---

## GPE-API-006

The API must protect Member and Platform Partner confidentiality.

---

## GPE-API-007

Retryable create and lifecycle actions must support idempotency.

---

## GPE-API-008

Contribution approval requires all applicable evidence, attribution, verification, country, limit, and compliance rules to pass.

---

## GPE-API-009

Duplicate business outcomes must not generate duplicate incentive eligibility unless shared attribution is explicitly approved.

---

## GPE-API-010

The Growth Partner API must not issue RP, create ABCs, distribute AHC, determine Hive placement, allocate Platform Revenue, or perform Financial Settlement.

---

## GPE-API-011

All significant administrative actions must create audit records and domain events.

---

## GPE-API-012

AI Agents must not receive permissions broader than the user or service identity they represent.

---

## GPE-API-013

Public endpoints may expose only approved public Growth Partner and Growth Program information.

---

## GPE-API-014

Administrative overrides require an explicit reason, elevated authorization, and immutable audit history.

---

## GPE-API-015

Historical Growth Program, Growth Partner Type, Scorecard, Contribution, and attribution versions must remain retrievable.

# Long-Term Vision

The Growth Partner Engine API should become the stable, secure, and reusable interface for every governed ecosystem-growth activity within AsBeez.

Future Growth Partner Types, Programs, Contribution models, countries, strategic alliances, campaigns, AI assistants, and enterprise integrations should reuse the same API foundation while extending behavior through:

- Policies
- Versions
- Permissions
- Eligibility Rules
- Contribution Types
- Verification Rules
- Attribution Rules
- Entitlements
- Events

The API should support web, mobile, enterprise, integration, analytics, and AI consumers without exposing internal implementation details or weakening domain boundaries.

# Closing Statement

The Growth Partner Engine API provides governed access to the capabilities through which ecosystem growth is recorded, verified, measured, and recognized.

By exposing explicit business actions, protecting participant confidentiality, enforcing Growth Program rules, preserving immutable history, and integrating through trusted events, the API enables transparent ecosystem expansion without confusing contribution with reward issuance, ABC structure, revenue allocation, or financial settlement.

---

# Growth Partner API Principle

> **The Growth Partner API exposes verified growth capabilities—not hierarchy, automatic compensation, or database operations. Every action must respect Growth Program rules, participant ownership, attribution, evidence, privacy, authorization, auditability, and the boundaries separating contribution from Rewards, Revenue Allocation, Hive structure, and Financial Settlement.**
